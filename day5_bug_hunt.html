Drill 1 · The protocolE5-PRO-TR-?? ⚠

Five steps, every time

The Bug Hunt Protocol: Symptom (what actually happened) → Predict the cause → Trace to the exact line → One change → Re-run. The protocol exists so you never change three things at once. Try it on a symptom you already know:

SYMPTOM: a recruit's program prints   7777
         when the answer should be    28
Predict You met this exact bug on Day 1. Predict the cause, and name the one change that fixes it, before revealing.
The text trap: a number arrived through input() as text, and text times 4 repeats the digits. The one change: wrap the input in int() and decode on arrival. If you diagnosed that from the symptom alone, you already think like a bug hunter.
Drill 2 · The shared sabotaged programE5-PRO-TR-?? ⚠

Two loud bugs

The whole room hunts this one together. Copy it into bughunt.py exactly as written, bugs and all. It's the roster program for tonight's badge ceremony, and it carries four bugs: two loud, two silent. Read it, trace it, circle your suspects. Then run, and fix the loud ones first, one change per run.

recruits = ["Nightjar", "Falcon", "Osprey", "Wren"]
print("Recruits arriving for the badge ceremony:")
for i in range(1, 4):
    print(i, recruits[i])
badges = input("How many badges to engrave? ")
cost = badges * 5
print(f"Engraving cost: {cost} credits")
honoree = random.choice(recruits)
print(f"The Director's commendation goes to {honore}!")
Predict Type 4 when it asks. Which line misfires first, and what will the traceback's last line say? (Careful: the first crash may be further down than you think.)
The program runs surprisingly far (the greeting, three recruits, the question, even a cost line) and then crashes at the commendation: NameError: name 'random' is not defined, because the Dispatcher was never imported. Newer Pythons add a hint after the period: Did you forget to import 'random'? One change, import random at the top, and re-run. It crashes again one line later: NameError: name 'honore' is not defined. The briefcase was filled as honoree but read as honore. Fix the spelling. Two loud bugs fixed, two runs, two log rows. A loud bug at least tells you where it lives.

Drill 3 · Silent bug IE5-PRO-TR-?? ⚠

The cost that lies

No traceback this time, but look at the cost line. Badges cost 5 credits each and 4 were ordered. The program says 44444.

SYMPTOM:  Engraving cost: 44444 credits
EXPECTED: Engraving cost: 20 credits
Predict Run the protocol on paper: predict the cause, name the line, name the one change. What should the cost line say for 4 badges after the fix?
Drill 1's bug, hiding in tonight's program: badges is text, so badges * 5 repeats the digit instead of multiplying. The one change: badges = int(input("How many badges to engrave? ")). Re-run: Engraving cost: 20 credits. A silent bug never announces itself. You have to know what the answer should be, and that's what the schematic and your predictions are for.

Engraving cost: 20 credits

The recruit who was never called

Read the roster at the top. Now read the arrivals your program printed. Count them.

SYMPTOM:  1 Falcon / 2 Osprey / 3 Wren  (three recruits called)
EXPECTED: four recruits on the roster. Where is Nightjar?
Predict Which Day 1 bug is this, on which line, and what is the one change? After the fix, what number will print beside Nightjar's name?
The off-by-one. range(1, 4) deals 1, 2, 3, so slot 0 of the roster is never visited and Nightjar waits in the hall. The one change: range(4). Nightjar is called as recruit 0, because slot numbers start at 0, Day 1's law. Every bug today is an earlier lesson wearing a disguise.

Drill 5 · The wiretap ritualE5-PRO-TR-?? ⚠

The debugger: predict-before-reveal, built into VS Code

All week you predicted, then revealed. VS Code has that ritual built in. In your fixed bughunt.py: click in the gutter left of the cost = badges * 5 line so a red dot appears (a breakpoint). Then Run → Start Debugging, choose Python File, and answer the badge question. The program freezes at your dot, before that line runs.

THE RITUAL, AT THE FROZEN LINE:
1. PREDICT aloud: does the briefcase  cost  exist yet?
2. Look in the VARIABLES panel on the left.  (Reveal.)
3. Press F10 to step one line. PREDICT cost's value first.
4. Look again.  (Reveal.)  Press F5 to let the program finish.
Predict At the frozen moment, before F10, is cost in the Variables panel or not? And after one F10 step, typing 4: what exact value appears beside it?
Not there. A briefcase isn't born until its line runs, so you'll see badges: 4 waiting but no cost. One F10 step later, cost: 20 appears. The wiretap is your Field Notebook trace table, drawn live by the terminal itself. Use it on any bug the protocol can't corner.
Drill 6 · Triage your gadgetE5-PRO-PD-?? ⚠

The Bug Hunt Log

Now your own Commission goes on the table. Run your gadget. For every bug you meet, loud or silent, the log gets a row: Symptom | Predicted cause | Line found | The one change. If your gadget runs clean, congratulations: push it further (a second gate, a second routine, more beacons) and log whatever the new code stirs up. New features breed new bugs, and the log is exactly where they belong.

SYMPTOM: my beacons freeze in place, but the sweep keeps moving
Predict Bug Hunt warm-up: for that frozen-beacons symptom, which briefcase would you watch first in the wiretap: colors[i], ys[i], or BEACON_COUNT? Why that one?
ys[i]. Frozen beacons means positions stopped changing, and ys[i] is the briefcase that should shrink every pass. If it isn't changing, trace one step upstream: is the update line still inside the beacon loop? Did DRIFT_SPEED become 0? The symptom points to a briefcase, and the briefcase points to a line.
Hinge question · stop here until you're sureE5-PRO-TR-?? ⚠

The bug with no traceback

A program runs top to bottom with no error at all, and it is still wrong.
How is that possible, and what do you compare its output against to prove it?

A silent bug: the terminal did exactly what the code said, and the code said the wrong thing. 44444 credits; a missing Nightjar. You prove it by comparing what the program does against what you said it should do, using your schematic, your predictions, your expected output. If you can't say what the right answer should be, you can't say the program is wrong.
Fast-finisher build · The Three-Door Extraction

A pocket adventure, zero new syntax

Gadget fixed, log filled, time to spare? Build a terminal escape, three checkpoints with a choice at each, using only this week's tools:

1. A rich-tinted title and the agent's codename via input().
2. for checkpoint in range(1, 4): gives one pass per checkpoint.
3. At each checkpoint, ask left or right? and gate the reply with if pick in ["left", "l"]: and an else.
4. A rich-tinted extraction line with the agent's codename.

from rich import print

print("[bold green]THE THREE DOORS OF THE SAFE HOUSE[/bold green]")
codename = input("Agent codename: ")
for checkpoint in range(1, 4):
    print(f"[yellow]-- Checkpoint {checkpoint} --[/yellow]")
    pick = input("left or right? ")
    if pick in ["left", "l"]:
        print("A cold draft from the stairwell. The way is clear.")
    else:
        print("Footsteps behind the door. You slip past!")
print(f"[bold green]{codename} reaches the extraction point. Mission complete.[/bold green]")
Day 1's input, loop, and rack checkpoint, painted with Day 2's stretch ink (run pip install rich if you skipped it). Three counted checkpoints on purpose: an escape with a known length needs no watch loop.

The Final Debrief · closing block

Report before the Academy

The three-part debrief Each agent, in turn: (1) Run. Run your gadget for the room. (2) Point. On your signed schematic, show where the loop turns and where your gates decide. (3) Tell. Name one design choice you made, and read one row of your Bug Hunt Log aloud: the symptom, and the one change that fixed it.

A gadget that crashed on Thursday and runs on Friday is the better story. The log proves you can hunt bugs; read from it proudly. Badges follow the last debrief.

Choose your exit gate

Floor · approaching the standard

You fix both loud bugs in the shared program using the protocol, one change per run, with a log row for each.

Middle · meets the standard

All four bugs fixed, loud and silent. Your own gadget runs for the Debrief, and your Bug Hunt Log holds at least one real row from your own code, all four columns filled.

Stretch · exceeds the standard

The Three-Door Extraction runs, and you demonstrate the wiretap ritual to a classmate on their code: breakpoint, prediction spoken first, step, reveal.

Standards, pacing & evidence (teacher panel)

The pacing choice, stated plainly: no new syntax today either. Day 5 has one job, debugging, and every planted bug is an earlier lesson in disguise: the text trap and the off-by-one from Day 1, a missing import and a misspelled briefcase that the Day 1 traceback habit catches. The protocol is the week's predict-before-reveal structure turned into a repair tool, and the debugger is taught as a prediction instrument: the prediction is spoken before the Variables panel is consulted, every time.

Where recruits actually stall: Block A (Drills 1 to 4) runs about 45 minutes. The import bug surprises recruits because the crash sits far from the top; let them trace to it. The off-by-one needs counting out loud: four names, three greetings. Block B (Drills 5 and 6 plus the hinge) runs about 40 minutes; the debugger needs the Python extension, and the first Start Debugging asks for a configuration (choose Python File). Breakpoints in the gutter are the usual fumble. Block C, the Final Debrief and the badge ceremony, needs at least 50 minutes for a class of twenty: two and a half minutes per agent.
